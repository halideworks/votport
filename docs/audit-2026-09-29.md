# Delivery and application audit, 2026-09-29

The audit uses main `dece4969` as its baseline. It covers delivery preparation,
source identity and proof catalogs, active downloads, tenant outbound requests,
peer transfers, notifications, browser layout, and build output handling. The
existing Rust, JavaScript, browser, dependency, and CI checks cover the other
application surfaces. The original deployment checkout and its unrelated local
changes are preserved.

## Corrections

| Area | Defect | Correction |
| --- | --- | --- |
| Hash scheduling | Ordered task polling leaves hashing slots idle behind a large file. | Poll four tasks in completion order, then restore selection order before publishing the grant. |
| Library preparation | First delivery creation waits for every source byte to be hashed. | Prepare stable Library sources and proof catalogs in the background while transfers are idle, share per-source locks with foreground requests, and retain cached catalogs through startup and daily cleanup. |
| Received SHA-256 files | Preparation reads every source for BLAKE3 and then reads it again serially for SHA-256 verification. | Verify the original SHA-256 identity and prepare its catalog in one parallel pass. Ignore BLAKE3 cache entries for this verification. |
| Small files | The small-file hashing path allocates a 1 MiB read buffer even for files of at most 64 KiB. | Allocate no more than the file length, capped at 1 MiB. |
| Request execution | Selection filesystem operations and cache persistence run on async workers. | Move these operations to the existing blocking task pool. |
| Cache correctness | A same-size rewrite with restored mtime can reuse an obsolete root. | On Unix, include device, inode, and change time in validation. Recheck source metadata after hashing and enforce the current size limit before accepting a cached root. |
| Cache maintenance | Edited versions accumulate as separate entries; malformed sidecars can be oversized; failed persistence leaves staged files. | Keep one entry per tenant and path, cap sidecar input at 16 MiB and 8,192 entries, and remove failed stages. |
| Download extension | Active downloads retain their original expiry even after an operator extends the grant. | Refresh an elapsed deadline by the original token hash; retain revocation and rotation cancellation. Check the clock again after waiting for the store. |
| Library deletion | An ASCII delete request misses a Unicode source that folds to ASCII. | Apply the existing Unicode fold to the fallback scan of live grants. Keep per-chunk upload checks indexed. |
| Tenant egress | Trade inspection, enrollment, status, credential changes, route commands, revocation, and transfer traffic bypass tenant restrictions. | Use the existing restricted resolver for HTTP and apply the same address policy after resolving QUIC rendezvous targets. Allowed QUIC transfers remain available. |
| IPv6 egress | Several nonpublic address ranges pass the public-address test. | Reject addresses outside 2000::/3 and additional site-local, local translation, benchmark, and documentation ranges, preserving embedded IPv4 checks and explicit configured network allowances. |
| Notification delivery | SMTP phases can each finish within their timeout without a whole-attempt deadline. | Bound the entire destination attempt, including retries, to 30 seconds. |
| Notification layout | Help and result text sits against adjacent buttons. | Add shared CSS spacing and test the notification editor at 390 and 1,440 pixels. |
| Notification description | Inheriting defaults is described as enabled even when defaults may disable delivery. | Describe inheritance explicitly before and after saving. |
| S3 acceptance fixture | The pinned MinIO distribution image returns HTTP 401 before application tests can run. | Build the same MinIO release from immutable official source using digest-pinned Go and runtime images, preserve its license, and retain the CPU v1 baseline. |
| WASM build | The binding step assumes the default Cargo output directory. | Resolve absolute, relative, and default `CARGO_TARGET_DIR` values; test paths containing spaces. |

No application dependency or database schema changes are required. The fixes use existing
resolvers, object builders, proof generation, task pools, cancellation tokens,
CSS, and standard library facilities. The obsolete second hashing path and
cache version keys are removed.

## Hashing measurements

Measurements use the same host, release builds, an authenticated delivery-grant
request, and three repetitions per case. Each case starts a fresh server and
then creates a second grant from the unchanged source. Timings include grant
preparation. Cold means an empty application root cache; the operating system
and ZFS caches are uncontrolled. Fixtures contain generated data on temporary
NVMe storage, not production media or the production eight-disk RAIDZ2 pool.

The generated 60 GiB fixture has 15 files of 4 GiB each. The exact Library
selection later supplied by the operator has 17 files totaling 69.398 GB
(64.63 GiB); its largest file is 33.548 GB. The generated fixture does not
reproduce that size distribution. Large-file first hashes must read every source
byte; these timings do not separate storage time from hashing CPU time. Repeat
grants already benefited from caching before this change; this audit strengthens cache validity rather than inventing that cache.

The foreground comparison uses baseline `dece4969` and audit revision
`0073a42`, before background preparation was added. Its tables label that
earlier audit build as Foreground fixes. The background preparation check below
uses the updated release source at `b4e77f5`.

The foreground audit release was measured with the other audit workers stopped. Baseline
and final builds alternate order between repetitions. Earlier runs that
interleaved with browser helper compilation are excluded from these results.
Other host activity and filesystem cache state remain uncontrolled.

| Selection | Baseline cold median | Foreground fixes cold median | Baseline cached median | Foreground fixes cached median |
| --- | ---: | ---: | ---: | ---: |
| 4,000 files of 4 KiB | 0.213 s | 0.108 s | 0.098 s | 0.104 s |
| One 1 GiB file | 0.233 s | 0.283 s | 0.0026 s | 0.0034 s |
| One 1 GiB file plus 4,000 small files | 0.402 s | 0.298 s | 0.093 s | 0.106 s |
| 15 files totaling 60 GiB | 61.04 s | 73.14 s | 0.0039 s | 0.0044 s |

Cold small-file and mixed selections improve in this run. The single-file cold
case is slower, and cached selections show no improvement. These results do not
support a universal hashing speedup. The final 60 GiB median is slower than the
baseline. Its cold runs range from 60.02 to 87.53 seconds, compared with 59.92 to
63.35 seconds for the baseline. No reliable first-hash gain is established for
the reported file count and volume. Source review found no additional full-file
reads or cryptographic work in the large BLAKE3 path; these measurements do not
identify the cause of the variation.

A separate concurrency experiment compared four readers with two readers on
this 60 GiB fixture. Median cold preparation was 26.40 seconds with four and
32.36 seconds with two; the two-reader version was slower and was discarded.
Four readers remain the limit. Earlier before/after measurements were
23.30 versus 22.33 seconds for 60 GiB, which is within observed storage variance.
No large-file first-hash speedup is claimed from scheduling alone. The SHA-256
change removes one complete source read; its benefit depends on the incoming
suite and storage throughput.

### Exact Library selection

A second comparison reads the exact 17 production source files without copying
media, changing their contents, using production application state, or creating
production links. Each immutable release binary runs with its own temporary
state on a loopback address. Three repetitions alternate baseline and final
order. Files use the Library's sorted selection order, with the largest file
first. Source sizes and mtimes remain unchanged. Application caches start empty;
operating system and ZFS caches remain uncontrolled.

| Exact 69.398 GB selection | Baseline | Foreground fixes |
| --- | ---: | ---: |
| First-hash median | 89.17 s | 89.63 s |
| First-hash range | 88.03 to 96.10 s | 89.51 to 90.62 s |
| Cached-share median | 0.0058 s | 0.0073 s |
| First-hash process CPU median | 61.20 s | 63.83 s |

The overlapping first-hash timings show no established speedup on this real
selection. The final median is about 0.5 percent slower. Caching remains the
large practical reduction for an unchanged selection, but both versions already
provide it. These measurements do not reproduce the application's state or
storage activity at the time of the original delivery. A separate two-reader
check took 90.51 seconds on this selection. That single run supplies no evidence
that lowering the reader limit helps; four readers remain the default.

### Background Library preparation

Background preparation is enabled by default and uses the existing Library path
admission, object builder, root cache, and proof catalog. It uses a 15-second
poll interval, scans between hashes while idle, and requires an unchanged
metadata stamp across that interval. A long hash delays the next scan. One
streaming hash runs at a time, checks transfer activity between 1 MiB reads, and
stops when HTTP or native transfers become active, shutdown begins, or the
instance loses its storage lease. Foreground preparation and background work
share a per-source lock and the existing four-slot hash limit. An aborted async
request retains its lock and slot until its blocking hash actually completes.

Startup and daily proof cleanup retain catalog names referenced by the bounded
root cache. Readiness checks validate catalog headers and physical lengths in
the blocking task pool; a missing or malformed catalog is prepared again through
the cancellable background path. Source rewrites reset the stability interval
and invalidate cache reuse. Preparation creates no delivery grants or links.

The worker skips symlinks, private snapshots, disallowed hidden or nonportable
components, temporary extensions, and files above the configured size limit.
The shared traversal keeps its existing 100,000-node and 128-level limits.
Background work retains the newest 4,096 discovered candidates, leaving half of the
8,192-entry cache for foreground selections. Larger libraries may need an
explicit folder scope or a larger cache. `VOTPORT_LIBRARY_PREHASH=false`
disables background reads. A stable interval is a preparation heuristic, not a
signal that an external producer has finished writing; later metadata changes
invalidate the cached result.

An isolated check on the same exact 17-file Library selection allowed the
background worker to prepare all sources before creating any delivery grant.
All roots and catalogs were persisted after 107.04 seconds, including the
15-second stability wait. Other browser acceptance work was running during this
check, so its preparation time is not a controlled comparison with the earlier
cold benchmarks.

Three subsequent grant requests took a median of 0.0348 seconds (range 0.0331 to
0.0486). Each added only 1,920 bytes to the server process's `rchar` counter,
rather than rereading 69.398 GB of media. Restarting that isolated server with
the same temporary state retained all 17 catalogs through startup cleanup. After
one further scan interval, three requests took a median of 0.0039 seconds (range
0.0033 to 0.0077), with at most 34,688 bytes read by the process. Source sizes and
mtimes remained unchanged; the temporary state and both servers were removed.
The restart check includes the grants created in the first measurement. A
separate regression reloads the root cache and runs proof cleanup without any
grants, retaining the cached catalog and removing an orphan. It also verifies
cancellable repair of a malformed catalog. The measurements establish cache
reuse before the first operator share and across a restart, not faster raw
hashing or a prediction of production request latency.

## Validation

Rust formatting, Clippy with warnings denied, full server and native client test
suites, and the separate low-file-descriptor regression pass. All 73 JavaScript
tests pass with no skips. ESLint, design-token checks, real WASM generation,
Cargo dependency policy checks for both workspaces, and the npm advisory check
pass. All nine Chromium acceptance suites pass against immutable final binaries
and isolated loopback fixtures.

Real S3 import/export, conditional mutation rejection, retry, literal keys, and
backup inventory/restore checks also pass against the source-built fixture with
configured, ambient, and saved credentials. The fixture uses the official
[MinIO release source](https://github.com/minio/minio/tree/07c3a429bfed433e49018cb0f78a52145d4bedeb).

The native QUIC policy regression was also checked by removing its address
filter: the UDP fixture received a packet and the test failed in 2.1 seconds.
Restoring the filter passed. Independent source and report reviews are complete.

## Operational limits

The cache format changes to version 2. Existing sidecars are ignored, so the
sources must be prepared again once, either in the background or during the first subsequent share. Received SHA-256 files always
verify source bytes and do not take the BLAKE3 cache shortcut.

An SMTP attempt can time out after some recipients have accepted the message.
A retry may duplicate those deliveries; the timeout is not proof of non-delivery.

Named-tenant peers on private networks need the existing explicit private-network
allowlist. Platform-configured receive destinations retain their existing
network policy. IPv6 filtering is conservative about nonpublic allocations.

On non-Unix servers, cache identity still uses size and mtime. Download integrity
checks remain in place, but this fallback cannot detect every preserved-mtime
rewrite during preparation. Production uses Unix metadata.

Already admitted QUIC downloads still depend on the upstream VOT cancellation
interface to stop immediately on revocation. HTTP streams stop at their checked
frame boundaries. No change to the upstream dependency or desktop installer
publication is included in this release.

A full pass and passing checks do not establish that every possible application
bug is absent. The changes above have targeted regressions and independent
source review. The isolated measurement on the exact Library selection shows
no established first-hash gain, and storage activity during the original
delivery remains unmeasured.
